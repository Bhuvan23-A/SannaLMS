Sanna LMS Review and Correction Register
Review scope and evidence limits
This is a production read-only Super Admin UI review, not a completed functional UAT, security audit, or capacity certification. Every visible top-level menu was visited. Available list pages, representative filters, safe form views, course management tabs, a section roster, an existing test submission and response review, a closed forum, certificate verification, and relevant empty states were inspected. No users or records were created; nothing was edited, deleted, archived, promoted, published, recalculated, issued, revoked, uploaded, sent, or marked read. Credentials were entered by the user. No load or attack tests were run.
The user confirmed that only the current Super Admin session is available. Student, Trainer and College Admin UX and permission enforcement remain unvalidated. Buttons that can alter production data were inventoried but not executed. Save validation, import execution, bulk operations, recovery, notification delivery, live classroom joining, GPS attendance, and end-to-end grade calculation need an approved staging environment. Not every record, edit dialog, filter combination, or state-dependent workflow was exercised. A comprehensive module review is delivered below, with those limits preserved rather than declaring all workflows passed.
Evidence labels: Observed = visible UI behavior or text; Needs validation = implementation or outcome not established by navigation; Proposed = improvement or requirement. Priority expresses potential business impact; it does not turn an untested risk into a confirmed defect.
1 Executive Summary
Go-live readiness is not established. Sanna LMS exposes a useful institutional and teaching structure, but Edulateral should withhold sign-off for a 10,000-user rollout or a 500-student simultaneous Online Test until the security, data integrity, grading and capacity gates below pass.
The most urgent observation is predictable credential provisioning: Bulk Import states that a student's phone number becomes the password, with a common fallback. College onboarding also describes a fixed temporary administrator password. Whether first-login password change is enforced was not established. These policies require immediate review and replacement with secure activation or unique short-lived credentials.
Reporting cannot currently be trusted without reconciliation. Dashboard displays 188 total enrollments and 2 active courses. User Directory shows 194 users, including 188 students. Both visible courses are DRAFT, their course enrollment tabs show 0, and Analytics reports 0 enrollments and 0 quizzes, despite visible Online Tests and an existing submission. Different data models or scopes may explain some differences, but the UI does not explain them.
Edulateral's Subject search and bulk-selection concerns are confirmed. Archive semantics are unclear: “Showing Archived” retained published and draft subjects and still offered Archive actions. Academic Sessions should be retained because courses and sections reference them; it needs clearer per-college semantics and a distinction from admission batches. Assessment Overview is currently a navigation landing page and can be simplified. The Question Bank template button already exists, although a completed download was not captured during this session.
Gradebook is not operationally self-explanatory: populated assessment submissions coexist with an empty calculated-grade view, with no visible grading formula, weighting or calculation history. Engagement tools offer practical uses, but Analytics is limited to counts and recent courses; no separate Rewards implementation is exposed.

Archived Subjects intended behavior versus observed behavior
The UI observation establishes only that the toggle changes its label and reloads a list that still includes active-looking records. It does not establish whether archiving is soft deletion, hides new-course selection, blocks ongoing learning, or has a restore mechanism. Those effects were not tested because archiving changes production data.
Recommended contract: archiving retires a subject from future selection while retaining syllabus versions, existing offerings, enrollments, assessments, grades and certificates. Archived-only lists should provide status, reason, actor/time and Restore. Deletion should be separately permissioned and normally blocked when dependencies exist. Edulateral must approve this contract and verify it in staging.
Academic Sessions keep but clarify
Sessions are necessary for year/term-specific offerings, section rosters, promotion, reporting and historical results. The current implementation already links them to sections and courses. Removing the module would remove an important time boundary unless the same concept is implemented elsewhere.
Use separate concepts: University → Department → Program/Branch → Admission Batch → Academic Session/Term → Semester → Section → Course Offering, with Subject as the reusable curriculum definition. Allow training programs to use a shorter hierarchy. “One current session” should mean one within the explicitly configured institution/program scope, not one across all universities. An admission batch such as 2024–2028 is not a single annual session.
Gradebook how it should be used
Observed sequence: choose college and course → review Online Test submissions → inspect student answers, score and feedback → authorized grader uses Save & Release Grade → Gradebook exposes Recalculate Grades and CSV export → certificate batch workflow describes Gradebook-based calculation. Calculation and release were not executed, so their actual interaction remains unverified.
Recommended operating workflow:
Confirm correct subject, course offering, session, section and roster. Assign authorized trainers.
Approve a grade policy before publishing assessments: marks, weighting, pass criteria, late/missing work, rounding, retakes and grade scale.
Publish Online Tests and assignments to the intended cohort. Student receives attempt/submission receipt.
Auto-mark supported MCQs and have authorized graders assess essays/coding/projects. Keep draft grades separate from released grades.
Moderate and release scores/feedback using a recorded actor, timestamp and reason for overrides.
Calculate or refresh the course result using the approved policy. Show every component, marks/maximum, weight and contribution. Do not silently count an unattempted test as completed.
For semester GPA, combine finalized subject results using approved credit weights; cumulative GPA needs results from the defined historical scope. A single course percentage is not automatically a semester CGPA.
Review exceptions, lock/finalize results, export reconciled records, then issue certificates only to eligible students. Reopening a grade must record why and update downstream records deliberately.
Illustrative policy only: if Online Test is 40% and Assignment is 60%, a student scoring 30/60 and 80/100 obtains 0.4×50 + 0.6×80 = 68%. Edulateral must approve its own policy; this example is not a statement about the application's current formula. GPA should use an approved mapping and sum(credit × grade point)/sum(credits), with treatment of failures, repeats and excluded subjects documented.

Practical Analytics Rewards use cases
Analytics should answer: Which batch is not logging in? Which students have not attempted an Online Test? Which topics show low mastery? Which assignments await grading? 500 concurrent users is not a single requests-per-second number. Thirty-second autosaves average roughly 500/30 = 16.7 requests/s, while a five-second submission burst averages 100 submissions/s, before scoring, authentication, navigation, telemetry and retries. If submission is one shared deadline instant, the instantaneous burst can be larger. Model the measured browser/API workflow and actual payload sizes.
